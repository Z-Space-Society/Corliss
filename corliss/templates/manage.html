{% extends "base.html" %} {% comment %} The cluster console. Three tables that come from three completely different places, and the difference is the point: - Applications are read live from the registry's *index*, and are written by the applicants themselves. They carry no authority whatsoever. Only the ones still awaiting a decision are listed: an application record is permanent and reads the same however it was answered, so the member cache is what tells the answered ones apart — see `views._applications` for why that question is settled by time rather than by the mere existence of a cache row. - Members are Corliss's own cache — what this deployment believes. It can be stale, incomplete, or (in the orphan case) wrong. - Admins are read live from the registry's public roster record. No cache, no credential, nothing to go stale. Reconciliation is what makes the second agree with the record. Both tables show handles with the DID on the cell's title. The handle is a label — `membership.handles_for` resolves it for reading, and the DID stays the thing being displayed *about*, which is why it is one hover away and never absent from the page. The admins table lists only who holds the role now. Departed terms are in the record and are what `Roster.was_admin_at` reads; this table answers the other question, "who can decide membership today". {% endcomment %} {% block title %}Membership — ZAI{% endblock %} {% block content %}

Membership

Who this cluster believes is a member, and who is allowed to decide that. Membership is cached here; the membership registry (HappyView) is the authority.

Applications

Who is waiting for a decision. Each one is a public record in the applicant's own PDS, read live from the registry's index — a request, never an entitlement. Applications already answered are left out: the record itself reads the same however it was decided, so the member cache below is what tells them apart, and listing every one of them would make this a second copy of that table rather than a queue.

Admins

Who holds cluster admin right now, read live from the registry's public roster. Not stored here, and not a Django permission — removing an admin ends their authority going forward without invalidating the grants they already wrote, which is why departed terms are left in the record rather than shown here.
